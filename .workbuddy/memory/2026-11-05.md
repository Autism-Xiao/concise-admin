## 修复：非超管账号点击「退出登录」无法退出（页面卡死）

**现象**：用测试账号 `ceshi / 123456` 登录（后端返回 role=viewer、permissions=[]、menus=[]），登录后直接落到 `/errors/403`；此时点「退出登录」无反应，页面像卡住。

**根因**：`src/routes/_authenticated.tsx` 的 `PermissionGuard` 在退出瞬间仍挂在 React 树上，`pathname` 已变成 `/login`，它判定无权限 → `<Navigate to="/errors/403" replace>`；而 `/errors/403` 属于 `_authenticated`，`beforeLoad` 发现未登录 → 又 redirect 回 `/login`，两者互相跳转形成死循环（实测产生成百上千次 /login ↔ /errors/403 导航），主线程被导航风暴拖住，点击表现为「没反应」。只有非超管（`permitted` 为 Set，超管返回 null 直接放行）才触发，因此 admin 测不出来。

**改动**：
- `src/routes/_authenticated.tsx`：`PermissionGuard` 增加 `if (!isAuthenticated()) return null`，未登录时不再做权限跳转。
- `src/lib/auth.ts`：`logout()` 同时清除 `concise-tabs`（多标签页持久化），避免下个账号登录后恢复上个会话的标签。

**验证**：Playwright + 本机 Chrome 走真实登录（含验证码）→ 403 页 → 点退出，URL 单次跳 `/login`、localStorage 清空、无循环；桌面/移动端两个退出入口回归通过；`tsc --noEmit` 无报错。

**备注**：`ceshi` 属于访客角色（viewer），无菜单权限进 403 是预期行为（用户确认）；已顺手修复登录昵称退化——`login.tsx` 现在按 `nickname → realname → name → username` 取显示名，`api.ts` 的 LoginResult 补了 `realname` 字段。真实登录验证 `concise-name` 已存为「测试用户」，退出流程回归正常。

## 修复：刷新页面主题色闪烁（先默认黑再变森林绿）

**根因**：dev 模式下 `index.css` 由 JS 在运行时注入 head 末尾（晚于 `transformIndexHtml` 注入的主题色 style），`:root{--primary:黑}` 与注入的 `:root{--primary:绿}` 同优先级 (0,1,0)，按声明顺序后者被 index.css 覆盖 → 页面先默认色，React 挂载后 settings-provider 再写 style 才变绿。时序：绿(注入) → 黑(index.css 注入) → 绿(applyOverrides)。

**改动**：
- `src/lib/theme-presets.ts`：`buildThemeColorCss` 选择器 `:root`/`.dark` → `html:root`/`html.dark`，优先级 (0,1,1) > (0,1,0)，不受注入顺序影响（dev + build 都生效）。
- `vite.config.ts`：注入的 style 加 `id="app-settings-override"`（与 settings-provider 的 STYLE_ID 一致），运行时切换主题复用同一元素；切回 default 移除该元素即恢复默认色，不会残留旧主题（优先级提升后残留会盖过 index.css 默认值，故必须复用）。

**验证**：Playwright 从首帧（t≈26ms）采样 `--primary`：亮色全程 oklch(0.55 0.16 145)、暗色全程 oklch(0.65 0.14 145)，无默认色阶段；运行时切回 default 正确恢复 oklch(0.205 0 0)；tsc、eslint、build 通过，dist/index.html 确认带 id 的 html:root 注入。

**环境备注**：重启 dev server 时 vite 依赖优化触发沙箱 safe-delete 批量删除限制（node_modules/.vite/deps_temp 94 文件 > 50 阈值）导致进程崩溃；解法是先手动分批清空 `.vite` 缓存目录再启动。

## 改版：验证码收进弹框（省空间 + 每题换图）

**需求**：图形要能变；不要占满一屏；常驻 320x160 太费纵向空间，改成弹框。

**改动**：
- `features/auth/login.tsx`：表单里 320x160 的拼图换成一行触发条（h-9，与输入框同高同宽）。未验证显示盾牌图标 + 「点击完成安全验证」+ 右箭头；验证通过显示绿色对勾 + 「已验证」+ 右侧「重新验证」。点击打开 `Dialog`，弹框内才是 `SliderCaptcha`（仍 320 宽，非全屏，`w-auto max-w-[calc(100vw-1.5rem)] p-3 sm:p-5`）。验证成功 600ms 后自动关闭弹框（先让用户看到绿态）。每次打开弹框都是新挂载 → `autoRequest` 重新请求，后端程序化出图必然不同（已抓两次 bgUrl 对比确认）。
- `config/i18n.ts`：新增 `login.captchaTrigger/captchaVerified/captchaRetry/captchaDialogTitle/captchaDialogDesc` 中英文案，`login.captcha` 由「验证码」改为「安全验证」。
- 表单高度从约 400px 降到 228px。

**关键数据（写自动化测试时必看）**：rc-slider-captcha 的滑块行程是 `control 320 - 按钮 40 = 280`，拼图行程是 `320 - 拼图 60 = 260`，所以 **鼠标拖动 d px 时拼图只移动 d×260/280**。真人跟图调整无感，但脚本必须按 `d = gap × 280/260` 换算，否则 gap 越大偏差越大（gap=200 时差 14px 必失败）。

**后端接口特性**：`POST /v1/auth/captcha/verify` 一次失败后该 captchaId 立即失效（返回 413 验证码已过期），无法在同一张图上反复试 x。

**缺口识别法（10/10 命中）**：把 `bgUrl` 画到 canvas，逐列求 RGB 均值，缺口区间亮度约为其他区域的 55%；取「低于中位数 75% 的最长连续列区间」的左边界即为正确答案 x。

**端到端验证**：Playwright 走真实流程——打开弹框→识别缺口→拖动（按 280/260 换算）→ 弹框自动关闭、触发条变绿（emerald-600）；随后提交登录，请求体带 `captchaTicket`，后端返回「用户名或密码错误」（而非验证码错误），证明 ticket 被接受。暗色、375px 小屏、英文界面均无溢出。

## 拼图竖条：结论是「只能后端改」

**现状**：`puzzleUrl` 是 60×160 的整条竖带（alpha 全覆盖、内容为半透明黑色的背景暗化版），`bgUrl` 里的缺口也是同尺寸暗色竖条。视觉上像两条黑胶带。

**实测**：给 puzzle 加 `border-radius:12px` + 白描边后，圆角卡片和直角缺口对不上，比原样更违和 → 纯 CSS 修饰无效。

**结论**：形状由后端画 PNG 时决定，前端只能平移与装饰。要换成拼图/圆形/方块，必须后端：puzzle 用带 alpha 的形状（如 60×60 圆角方块）+ 只保留一块区域的内容，bg 缺口用同形状填充（半透明黑 + 1px 白描边 30%），两者形状必须一致。前端 canvas 重绘是可行的兜底（用亮度列算法定位缺口后重绘），但属 hack、后端一改图即失效，未实施。
